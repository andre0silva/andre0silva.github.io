Acesso restrito em férias: Acesso Condicional + Lifecycle Workflows

Como deixar o colaborador em férias entrar em uma única aplicação e bloquear todo o resto, sem grupo dinâmico, com associação automática pelo atributo que vem do RH.

00Antes de começar

Sêniornível

Pedido comum do negócio: "a conta de quem está de férias fica bloqueada, mas essa pessoa precisa continuar acessando o app X (holerite, benefícios, escala)". A primeira ideia é liberar uma exceção no Acesso Condicional para a conta bloqueada. Não funciona, e entender o porquê define todo o desenho.

01Por que não dá para liberar uma conta desabilitada

  • Conta com accountEnabled = false não recebe token para nenhuma aplicação integrada ao Entra ID. O login falha com AADSTS50057 – UserDisabled.
  • Em contas sincronizadas, esse estado vem do Active Directory: desabilitou no AD, desabilita no Entra no próximo ciclo do Connect Sync.
  • O Acesso Condicional é avaliado depois do primeiro fator. A conta desabilitada nem chega lá.
  • O Acesso Condicional só restringe (bloqueia ou exige controles). Não existe controle que conceda acesso negado pelo diretório.
Conclusão

Para liberar um app nas férias, a conta precisa ficar habilitada. O controle passa a ser: conta ativa + bloqueio de todos os recursos, exceto o app autorizado.

02Desenho da solução

RH (situação = férias)
  → provisionamento RH → AD: conta HABILITADA + atributo de situação com o código de férias
  → Entra Connect Sync: atributo publicado como extensão de diretório
  → LCW "Entrada em férias" (Attribute changes) → Add user to groups → GRUPO_FERIAS
  → Acesso Condicional: GRUPO_FERIAS → bloqueia tudo, exceto o app autorizado
Retorno:
  → atributo muda → LCW "Retorno de férias" → Remove user from selected groups

Os demais afastamentos (licença, suspensão etc.) continuam desabilitando a conta normalmente. Só a férias muda de tratamento.

Por que Lifecycle Workflows e não grupo dinâmico

O grupo dinâmico resolveria a associação, mas há ambientes que não podem ou não querem usá-lo (cota de licença, política interna, rastreabilidade). Com workflows, cada entrada e saída do grupo fica registrada no histórico do workflow, com usuário, horário e tarefa.

04Passo a passo

  1. Ajuste a regra de bloqueio do provisionamentoNa expressão de accountDisabled do app de provisionamento RH → AD, retire o código de férias da lista de situações que desabilitam a conta. Teste com Provision on demand e confirme no AD que a conta continua habilitada e o atributo tem o código de férias.
  2. Publique o atributo no Entra IDSe for um msDS-cloudExtensionAttribute* ou outro atributo não sincronizado, habilite-o como Directory extension no assistente do Entra Connect (Personalizar opções de sincronização › Recursos opcionais). Ele aparece no Graph como extension_<appId>_<atributo>. Se usar extensionAttribute1-15, ele já sincroniza por padrão.
  3. Crie o grupo estáticoGrupo de segurança, associação Atribuída, criado direto no Entra ID (cloud-only), sem membros. As tarefas de grupo do LCW não aceitam grupos dinâmicos, sincronizados do AD, habilitados para e-mail ou atribuíveis a funções.
  4. Crie o workflow de entradaModelo Employee job profile change, trigger Attribute changes no atributo de situação, escopo pelo código de férias, tarefa única Add user to groups. Detalhes na seção 05.
  5. Crie o workflow de retornoMesmo trigger, escopo "diferente do código de férias", tarefa única Remove user from selected groups.
  6. Habilite o agendamentoWorkflow e agendamento (isSchedulingEnabled) habilitados. Mudança de atributo só é detectada em workflow agendado: habilitado sem agendamento não roda para ninguém.
  7. Crie as políticas de Acesso CondicionalEm modo somente relatório. Detalhes na seção 06.
  8. Faça a carga inicialQuem já está de férias no dia da ativação não gera "mudança". Inclua essas pessoas por execução sob demanda ou pelo script da seção 07.
  9. Teste e ativeValide a matriz da seção 08 e só então mude as políticas para Ativado.

Remova as tarefas que o modelo traz por padrão (e-mail ao gestor, remoção de pacotes de acesso). O workflow de retorno também dispara quando a pessoa sai de férias para outro afastamento: ela sai do grupo e a conta é desabilitada pela regra do provisionamento, que é o comportamento esperado.

Bloqueio + All resources pede cuidado

O app autorizado pode depender de outros recursos (Microsoft Graph User.Read, APIs próprias). Teste o login completo em modo somente relatório e veja nos logs de entrada qual recurso foi avaliado antes de ativar.

A política de MFA existe porque a conta fica habilitada com o dono ausente: é exatamente o tipo de conta que um atacante usaria sem ninguém perceber.

07Carga inicial e reconciliação

Script que compara quem está de férias com quem está no grupo. Sem -Aplicar, só mostra a diferença.

param(
  [Parameter(Mandatory)] [string]$GroupId,
  [Parameter(Mandatory)] [string]$CodigoFerias,
  [Parameter(Mandatory)] [string]$ExtAttr,   # extension_<appIdSemHifen>_situacao
  [switch]$Aplicar
)
Connect-MgGraph -Scopes "User.Read.All","GroupMember.ReadWrite.All" -NoWelcome

$emFerias = Get-MgUser -All -Filter "$ExtAttr eq '$CodigoFerias' and accountEnabled eq true" `
  -ConsistencyLevel eventual -CountVariable total -Property Id,UserPrincipalName
$membros  = Get-MgGroupMember -GroupId $GroupId -All

$idsF = @($emFerias.Id); $idsM = @($membros.Id)
$incluir = $idsF | Where-Object { $_ -notin $idsM }
$remover = $idsM | Where-Object { $_ -notin $idsF }
"Em férias: {0} | Membros: {1} | Incluir: {2} | Remover: {3}" -f $idsF.Count,$idsM.Count,@($incluir).Count,@($remover).Count

if ($Aplicar) {
  $incluir | ForEach-Object { New-MgGroupMember -GroupId $GroupId -DirectoryObjectId $_ }
  $remover | ForEach-Object { Remove-MgGroupMemberDirectoryObjectByRef -GroupId $GroupId -DirectoryObjectId $_ }
}

Rode antes da ativação (modo aplicar) e depois semanalmente (modo relatório). Divergência diferente de zero indica falha de workflow para investigar no histórico.

09Limitações e erros comuns

  • Recursos locais não são cobertos. Com a conta habilitada, logon em estação do domínio, VPN via RADIUS/LDAP, compartilhamentos e apps Kerberos continuam funcionando. Use um grupo equivalente no AD com GPO de negação de logon e regra de negação na VPN.
  • Não é imediato. Some o ciclo do provisionamento, o Connect Sync, até 4 horas de propagação de atributos personalizados para o LCW e o intervalo de agendamento do workflow (configurável de 1 a 24 h). Tokens já emitidos valem até expirar.
  • Carga inicial esquecida. Quem já estava de férias na ativação não entra no grupo sozinho.
  • Grupo errado. Grupo dinâmico ou sincronizado do AD faz a tarefa do workflow falhar.
  • Workflow sem agendamento. Fica "habilitado" e nunca processa ninguém.
  • Regra case-sensitive. "Ferias" e "FERIAS" são valores diferentes no escopo.
  • Exceção não formalizada. Se a norma diz "afastado = conta desabilitada", registre que férias passa a ser "conta habilitada com acesso restrito".
