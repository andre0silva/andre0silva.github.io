IGA com Microsoft Entra ID Governance: implantação passo a passo

Roteiro objetivo para colocar governança de identidade em produção: ciclo de vida a partir do RH, aplicativos integrados, pacotes de acesso, revisões de acesso e acesso privilegiado com PIM.

IGAJoiner · Mover · LeaverEntitlement managementAccess reviewsPIM

00Antes de começar

IGA (Identity Governance and Administration) é o conjunto de processos e controles que garante que cada identidade tenha o acesso certo, pelo tempo certo, com evidência para auditoria. No Microsoft Entra, isso responde a quatro perguntas:

  1. Quem deve ter acesso a quais recursos?
  2. O que essas identidades estão fazendo com esse acesso?
  3. Existem controles para gerenciar o acesso?
  4. O auditor consegue comprovar que os controles funcionam?

A implantação cobre três ciclos de vida: identidade (entrada, mudança e saída da pessoa), acesso (o que ela recebe além do básico) e acesso privilegiado (administradores).

01Preparar o locatário

  1. Arquitetura de locatárioDecida em qual locatário cada aplicativo e os parceiros externos serão governados, considerando requisitos de colaboração ou isolamento.
  2. Licenças atribuídasConfirme a combinação de licenças acima e atribua por grupo.
  3. Logs no Azure MonitorO Entra guarda auditoria por apenas 30 dias. Envie os logs de auditoria e entrada para um Log Analytics para ter histórico, pastas de trabalho e consultas.
    Entra ID›Monitoring & health›Diagnostic settings
  4. Retenção de objetosSe for preciso provar quem teve acesso a um app há um ano, incluindo contas já excluídas, planeje exportar os dados para Azure Data Explorer.
  5. Revisar funções privilegiadasAntes de tudo, confirme quem está em Global Administrator, Identity Governance Administrator, User Administrator, Application Administrator, Cloud Application Administrator e Privileged Role Administrator. Essas funções conseguem alterar atribuições de apps.
  6. Isolar a administração da nuvemContas administrativas da nuvem não devem ser contas sincronizadas do AD local. Isso protege o Microsoft 365 contra um comprometimento do ambiente local.
  7. Atributos de RH no EntraGaranta que employeeHireDate, employeeLeaveDateTime, department, jobTitle, employeeType e manager estejam preenchidos e confiáveis. Todo o resto da automação depende deles.

02Ciclo de vida da identidade

  1. Provisionamento a partir do RHConecte o sistema de RH (SuccessFactors, Workday ou via API de provisionamento de entrada) para criar, atualizar e desativar contas no AD e no Entra ID automaticamente. O RH vira a fonte autoritativa.
    Entra ID›Enterprise apps›New application (ex.: SAP SuccessFactors to Active Directory User Provisioning)
  2. Fluxos de trabalho do ciclo de vidaAutomatize tarefas nos eventos de entrada, mudança e saída: gerar Temporary Access Pass e enviar ao gestor antes do primeiro dia, e-mail de boas-vindas, adicionar a grupos e Teams, remover licenças e grupos no desligamento, excluir a conta depois de X dias.
    ID Governance›Lifecycle workflows›Create workflow
  3. Atribuição automática por atributoUse políticas de atribuição automática em pacotes de acesso para dar e retirar grupos, funções de app e sites SharePoint conforme departamento, cargo ou centro de custo. Mudou o atributo, mudou o acesso.
  4. Provisionamento para aplicativosCrie, atualize e remova contas nos sistemas de destino via SCIM, LDAP, SQL ou conectores da galeria (seção 04).

Convidados também têm ciclo de vida

Para parceiros e fornecedores, use o entitlement management (seção 05): o convidado é criado quando o pedido é aprovado e removido quando o acesso expira. Revisões de acesso fazem a limpeza dos convidados antigos.

03Definir as políticas de acesso

Antes de configurar qualquer coisa, documente com os donos de negócio, compliance e risco quem deve ter acesso a cada aplicativo crítico.

  1. Levantar funções do aplicativoListe as funções e permissões que cada app expõe (ex.: Usuário, Administrador) e se ele usa funções de app, grupos ou declarações no token.
  2. Escolher o que será governadoPriorize funções e grupos com acesso privilegiado ou a dados sensíveis.
  3. Pré-requisitos e aprovadoresQuem pode pedir (funcionário, área, centro de custo, externo) e quem aprova (gestor, dono do recurso, segurança), com uma ou mais fases.
  4. Duração e expiraçãoAcesso permanente com revisão anual, ou acesso por projeto com data de término.
  5. Separação de funções (SoD)Pares de funções incompatíveis que a mesma pessoa não pode ter.
  6. Acesso CondicionalMFA, dispositivo conforme, local e termos de uso exigidos para entrar no app.
  7. ExceçõesAuditores, fornecedores, viagens: política separada, com aprovador e prazo próprios.

Modelo de matriz para preencher por aplicativo:

Se a empresa já tem um modelo de funções organizacionais (RBAC por cargo/área), planeje migrá-lo para pacotes de acesso com atribuição automática.

04Integrar os aplicativos

Um app só é governável de verdade quando depende do Entra ID para SSO (o Entra emite o token) ou para a lista de usuários e grupos (provisionamento, Graph ou grupos do AD via Kerberos).

  1. Verificar se o app já existeProcure em Entra ID›Enterprise apps e em App registrations.
  2. Configurar o SSOApp da galeria: siga o tutorial do app. App próprio: OpenID Connect ou SAML. App local: SAML, IWA ou cabeçalho via Application Proxy. SAP BTP: via SAP Cloud Identity Services. SAP GUI: SAP Secure Login Service ou Entra Private Access.
  3. Definir funções de appCrie as funções no manifesto do app e atribua cada usuário à sua função. Se a pessoa pode ter várias funções ao mesmo tempo, prefira grupos de segurança.
  4. Configurar o provisionamentoEscolha o conector conforme o app:
O app usaIntegração
SCIM na nuvemProvisionamento SCIM direto
SCIM localAgente de provisionamento local + SCIM
Banco SQL próprioAgente de provisionamento + conector SQL
Diretório LDAPAgente de provisionamento + conector LDAP
API SOAP/RESTConector de serviços web
Grupos do AD (Kerberos)Group writeback do Entra Cloud Sync para o AD
SAP Cloud Identity ServicesProvisionamento SCIM para o SAP CIS
SAP ECC (NetWeaver AS ABAP 7.0+)Conector de serviços web para SAP ECC
  1. Exigir atribuiçãoDefina Assignment required? = Yes no app. Sem isso, qualquer usuário do diretório entra e não há o que revisar.
    Enterprise apps›<app>›Properties

Revisão inicial (linha de base)

Se o app já estava em uso, há acessos concedidos de forma manual ao longo dos anos. Antes de abrir pedidos de acesso, faça uma revisão de todos os usuários atuais:

  • App com banco ou LDAP próprio: importe os usuários existentes e crie as atribuições de função no Entra.
  • App sem provisionamento: obtenha a lista de usuários do app e crie as atribuições para cada um.
  • App com grupos do AD: revise esses grupos; ao final, remova os negados manualmente ou migre para grupo do Entra com writeback.
  • Resultado: todos os acessos revisados pelo menos uma vez. Só então siga para a seção 05.

05Gerenciamento de direitos

Pacote de acesso é o "kit" de grupos, funções de app e sites SharePoint que alguém precisa para uma função ou projeto. A política do pacote define quem pede, quem aprova, por quanto tempo e quando revisa.

  1. Criar o catálogoUm catálogo por domínio de negócio ou cenário. Delegue a dona do negócio como proprietária do catálogo.
    ID Governance›Entitlement management›Catalogs
  2. Adicionar recursos ao catálogoO app e todos os grupos dos quais ele depende.
  3. Criar um pacote por função/grupoA primeira política deve ser de atribuição direta (só administradores atribuem), já com revisão de acesso configurada.
    Entitlement management›Access packages›New access package
  4. Configurar SoDMarque pacotes ou grupos incompatíveis. Para exceções, crie um pacote de override com aprovação reforçada.
  5. Migrar os usuários atuaisAtribua ao pacote, pela política direta, quem já tinha o acesso. Em massa, use Graph ou PowerShell.
  6. Abrir pedidosAdicione políticas de solicitação com aprovação em uma ou mais fases, justificativa, expiração e revisão recorrente. Usuário pede em myaccess.microsoft.com.
  7. ExternosDefina as organizações conectadas que podem solicitar. O convidado é criado na aprovação e removido quando o último acesso expira.
  8. AutomaçãoPolíticas de atribuição automática por atributo, configurações de ciclo de vida com data, e Logic Apps para fluxos customizados (abrir chamado, criar conta em sistema legado).
Privilégio mínimo para administrar

Use a função Identity Governance Administrator em vez de Global Administrator. Para áreas de negócio, delegue como Catalog owner ou Access package manager.

Montar a revisão

  1. EscopoRecurso e quem será revisado: todos ou somente convidados.
    ID Governance›Access reviews›New access review
  2. RevisoresDono do recurso, gestor, revisor indicado ou o próprio usuário (autoavaliação). Com gestor ou dono, defina revisores de fallback. Não muda depois de iniciada.
  3. Frequência e prazoMensal, trimestral, anual. Revisões frequentes demais ou com poucos revisores viram "aprovar tudo".
  4. E-mail personalizadoMensagem curta explicando quem pede, o que se espera e onde há material de apoio. Revisores atuam em myaccess.microsoft.com.
  5. RecomendaçõesHabilite as recomendações baseadas em último login (ex.: sem entrada interativa em 90 dias) e, com licença Governance, afinidade usuário-grupo e usuários inativos.
  6. Ação automáticaAuto apply results to resource remove automaticamente quem foi negado. Defina também o que acontece se o revisor não responder.

Grupos sincronizados do AD

Revisões não alteram grupos cuja origem é o AD local. Revise mesmo assim e aplique o resultado manualmente (CSV ou Graph + PowerShell) até migrar para grupos do Entra com writeback.

Revisões que não podem faltar: convidados em grupos e Teams, membros de grupos de exclusão de Acesso Condicional, e todas as funções privilegiadas.

07Acesso privilegiado com PIM

  1. Inventariar atribuiçõesListe quem tem funções do Entra, funções do Azure e grupos privilegiados.
    ID Governance›Privileged Identity Management
  2. Converter para elegívelTroque atribuições permanentes por elegíveis: o administrador ativa a função só quando precisa (just-in-time). Mantenha permanentes apenas as contas de emergência.
  3. Configurar a ativaçãoPor função: duração máxima (ex.: 4 h), MFA ou contexto de autenticação, justificativa, número do chamado e aprovação para as funções mais críticas.
  4. Notificações e alertasAvisos de ativação para a segurança e alertas de atribuições fora do PIM.
  5. Revisões recorrentesRevise trimestralmente pelo menos: Global Administrator, User Administrator, Privileged Authentication Administrator, Conditional Access Administrator, Security Administrator e administradores de serviços M365/Dynamics. Inclua atribuições elegíveis e ativas.
  6. Grupos privilegiadosUse PIM para grupos quando o acesso administrativo é concedido por associação a grupo.

08Monitorar e automatizar

  • Atribuições fora do processo: monitore no Azure Monitor atribuições de função de app e mudanças de grupo que não vieram do entitlement management. Questione o dono do app.
  • Contas criadas direto no app: em apps com banco ou LDAP próprio, confirme que todas as contas vieram do provisionamento do Entra. Use a descoberta de contas para achar órfãs.
  • Aprovadores e revisores atualizados: quem saiu da empresa ou mudou de área precisa ser trocado nas políticas.
  • Revisões concluídas: acompanhe a taxa de decisão. Revisor que não decide é sinal de processo mal desenhado.
  • Desprovisionamento: verifique nos logs de provisionamento que os negados foram removidos do app de destino.
  • Auditoria: filtre logs de auditoria por categoria Policy e atividades de revisão (criar, aprovar, negar, aplicar decisão).
  • Relatórios: atribuições por pacote, histórico de mudanças (Azure Monitor), entradas dos últimos 30 dias por app, relatórios históricos no Azure Data Explorer.
  • Automação: módulo Microsoft.Graph.Identity.Governance com Azure Automation para tarefas agendadas; Graph Explorer para validar consultas antes de levar ao script.
  • Identidades de agente (IA): agentes com Entra Agent ID são governados pelos mesmos pacotes de acesso, com um patrocinador humano responsável, que passa para o gestor se o patrocinador sair.

09Piloto e implantação em ondas

  1. Escopo pequenoUm app não crítico, um grupo de usuários e revisores engajados.
  2. Sem ação automática no inícioRevise com aplicação manual dos resultados até entender o impacto.
  3. E-mails válidosConfirme que todos os usuários e revisores têm e-mail no Entra e recebem as notificações.
  4. Registrar remoçõesDocumente todo acesso removido no piloto para restaurar rápido se necessário.
  5. Comunicar a mudança culturalA decisão de acesso passa da TI para o dono do negócio. Treine os revisores e mostre como usar as recomendações.
  6. ExpandirApp por app, área por área, ligando a ação automática quando o processo estiver estável.
